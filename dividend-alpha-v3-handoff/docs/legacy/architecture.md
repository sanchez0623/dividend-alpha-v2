## 2. 模块职责矩阵

| 模块 | 职责 | 输入 | 输出 | 关键约束 |
|---|---|---|---|---|
| `da_data` | 数据接入、清洗、复权、落库 | 外部数据源 | 规范化行情/基本面 | 幂等、可回补、记录数据版本 |
| `da_factor` | 因子计算 | 行情 + 基本面 | `factor_daily` 表 | 只用**披露日之前**可得数据 |
| `da_signal` | 信号生成 | 因子 + 60min行情 | `signal` 表 | 必须计算 `expected_net` |
| `da_portfolio` | 目标权重、再平衡、下单建议 | 因子 + 持仓 | `order_intent` | 换手率上限、行业上限 |
| `da_risk` | 风控校验 | 订单意图 + 持仓 | 放行/拦截/降级 | 硬约束不可绕过 |
| `da_backtest` | 回测执行 | 策略配置 + 历史数据 | `backtest_run` | Broker 必须实现 T+1 |
| `da_attribution` | 归因与对比 | 回测/实盘成交 | 归因报告 | 对照组成立才可下结论 |
| `da_notify` | 告警推送 | 信号/风控事件 | 消息 | 去重、限流、分级 |

## 3. 技术选型与理由

| 领域 | 选择 | 备选 | 选择理由 |
|---|---|---|---|
| 语言 | **Python 3.11** | — | 量化生态最全；3.11 性能提升显著 |
| 计算 | **polars** | pandas | 全市场因子计算快 5-10×，内存友好，惰性求值 |
| 时序库 | **TimescaleDB** | InfluxDB / ClickHouse | 基于 Postgres，SQL 兼容，超表自动分片，压缩比高 |
| 研究态 | **DuckDB + Parquet** | — | 单机 OLAP，离线回测秒级扫全市场 |
| API | **FastAPI** | Flask | 自带 OpenAPI 文档、异步、Pydantic 校验 |
| 任务 | **Celery + Redis** | APScheduler | 需要重试、长任务、分布式；Beat 做定时 |
| 回测 | **自研事件驱动** | backtrader | backtrader 对 T+1/分批/FIFO 税的支持改造成本高，自研更可控 |
| 优化 | **cvxpy**（可选） | 启发式贪心 | 行业约束下的权重优化，规模小贪心也够 |
| 前端 | **React + TS + ECharts** | Vue | 图表生态、类型安全 |
| K线 | **lightweight-charts** | ECharts K线 | TradingView 出品，体积小、性能好、标注 API 灵活 |
| 部署 | **Docker Compose** | K8s | 单机足够；后期可平滑迁 K8s |

### 为什么回测引擎必须自研

通用框架（backtrader / zipline）都不原生支持以下 A 股刚需：

1. **T+1 可用仓位**：需区分 `shares_total / shares_locked_today / shares_available`
2. **FIFO 红利税**：卖出时按先进先出匹配买入批次，按**持股天数**决定 0%/10%/20% 税率
3. **分批成交与涨跌停不可成交**：需模拟撮合
4. **成本模型可插拔**：印花税/佣金/过户费/滑点分开建模

这四点决定了"做T是否真的赚钱"，交给通用框架会让结论失真。

## 4. 运行模式与调度时序

### 交易日时间线（Asia/Shanghai）

| 时间 | 任务 | 频率 | 说明 |
|---|---|---|---|
| 08:30 | 拉交易日历 + 复权因子 + 停牌/ST 状态 | 每日 | 盘前准备 |
| 09:30 / 10:30 / 11:30 / 13:30 / 14:30 | 拉 60min 快照 | 每 30 分钟 | **准实时监控核心** |
| 09:35-14:55 | 扫描做T信号 | 每 15 分钟 | 只在"有机动仓/有底仓"的标的上跑 |
| 15:05 | 拉当日日线 + 分钟线 | 每日 | 收盘数据 |
| 15:30 | 增量更新因子 + 生成次日选股池 | 每日 | |
| 15:40 | 生成订单意图（次日执行） | 每日 | 需人工确认或自动执行 |
| 16:30 | 净值结算 + 基准同步 | 每日 | |
| 17:00 | 绩效归因重算 + 日报推送 | 每日 | |
| 每周六 02:00 | 全量因子重算 + 周报 | 每周 | |
| 每季度末 | 核心仓再平衡 | 季度 | 低频，降低换手与红利税 |
| 每月 01 日 03:00 | 参数敏感性扫描 + Walk-Forward 前推 | 每月 | 防过拟合 |

### 三种运行模式

| 模式 | 说明 | 用途 |
|---|---|---|
| `backfill` | 批量历史回补 | 初始化、补数据 |
| `realtime` | 常驻调度，盘中扫描 | 实盘监控 |
| `research` | 离线批量回测/参数扫描 | 策略迭代 |

## 5. 部署拓扑

```yaml
# infra/docker-compose.yml（节选）
services:
  timescaledb:
    image: timescale/timescaledb:2.15.2-pg16
    environment: [POSTGRES_PASSWORD=${DB_PASSWORD}]
    volumes: [pgdata:/var/lib/postgresql/data]
    ports: ["5432:5432"]

  redis:
    image: redis:7-alpine
    ports: ["6379:6379"]

  api:
    build: .
    command: uvicorn da_api.main:app --host 0.0.0.0 --port 8000
    depends_on: [timescaledb, redis]
    ports: ["8000:8000"]

  worker:            # Celery worker，可横向扩容
    build: .
    command: celery -A da_core.celery_app worker -l info -Q data,signal,backtest
    depends_on: [redis, timescaledb]

  beat:              # 定时任务调度
    build: .
    command: celery -A da_core.celery_app beat -l info

  web:
    build: ./web
    ports: ["5173:5173"]
```

## 6. 容量与性能估算

| 项目 | 规模 | 说明 |
|---|---|---|
| 股票数 | ~5,400 只（全 A） | |
| 日线 | 5400 × 250 天/年 × 15 年 ≈ **2,000 万行** | ~2 GB |
| 60min 线 | 5400 × 4 根/天 × 250 × 5 年 ≈ **2,700 万行** | ~3 GB（保留 5 年即可） |
| 因子表 | 5400 × 250 × 15 ≈ 2,000 万行 × 30 列 | TimescaleDB 压缩后 ~1.5 GB |
| 全市场日线因子计算 | polars 惰性求值 **< 30 秒** | |
| 盘中信号扫描（持仓 ~25 只） | **< 2 秒** | 只扫持仓，不扫全市场 |
| 全市场 15 年日线回测 | **< 60 秒**（向量化）/ **3-10 分钟**（事件驱动） | |

**关键优化**：
- 盘中只计算**持仓标的**的信号，全市场扫描留给盘后 —— 这是保证"准实时"的前提
- 因子结果缓存到 Redis（TTL 到下一交易日）
- 60min 表按 2 年一个 chunk 分区，冷数据压缩

## 7. 可观测性

| 层面 | 工具 | 监控项 |
|---|---|---|
| 日志 | structlog → JSON | 结构化，含 `trace_id` |
| 指标 | Prometheus + Grafana | 任务耗时、信号数、数据源成功率 |
| 告警 | da_notify | 数据源断流、任务失败、回撤熔断触发 |
| 数据质量 | 自检任务 | 缺失率、异常跳变、复权因子突变、停牌未更新 |

**数据质量硬校验（每日 15:05 执行）**：
```
1. 当日日线覆盖率 ≥ 99%（剔除停牌）
2. 复权因子环比变化 > 20% 的标的进入人工复核队列（可能除权/配股）
3. 分红记录 ex_date 缺失告警
4. 财务数据披露日晚于报告期的比例检查
```

## 8. 安全与配置

- 所有密钥走环境变量，`.env` 不入 Git
- 数据库最小权限：app 账号无 DDL 权限（迁移用独立账号）
- 策略配置 YAML 有 schema 校验（Pydantic），启动即验证
- 配置变更记录到 `config_audit` 表，回测结果可追溯到具体配置版本
- **回测结果必须记录 `config_hash`**，否则无法复现
